# iPhone Safari code submission recovery

The owner reported the generic account error screen after entering a recovery code in iPhone Safari. The recovery email was delivered from `no-reply@ledgerleagues.com`. At inspection, the account had no subsequent successful verification, and Vercel showed the email-request POST but no code-verification POST. The owner then confirmed that the email's recovery link successfully opened the password-reset page on the same iPhone. The initial code failure's exact browser exception was not captured; it must not be described as a proven Safari defect or proven network interruption.

A definite defect was reproduced: a rejected verification action escapes `useActionState` and crashes the entire account route. The focused regression fails against the released form with `TypeError: Load failed`. The repaired form catches request failures, retains the submitted/autofilled code in component memory, leaves an explicit retry available, and offers a page reload for a fresh email. It explains when an action belongs to an outdated deployment. Framework redirects still propagate, so successful verification reaches password setup. No credential is automatically replayed, logged, put in a URL, or persisted in browser storage.

The existing encrypted server binding of email, flow and destination is preserved. Supabase still checks the credential and issues the session. No Auth setting, provider configuration, database migration, or password policy changes are part of this repair.

The disposable Auth browser suite now runs against `next build` / `next start`, including mobile WebKit, rather than only the development server. A new test switches tabs, interrupts a recovery-code POST, verifies the form survives with its code intact, and retries successfully to the password-entry page. Tab switching is an approximation; it does not emulate physical iOS suspending Safari while Mail is open. Final results and deployment identifiers belong in the completion handoff.
